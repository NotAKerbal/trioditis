# X

X (Twitter) direct messages, including encrypted **X Chat** conversations, through
**mautrix-twitter v0.2609.0** (`go.mau.fi/mautrix-twitter`, `TwitterConnector`). Network ID
`twitter`, maturity **experimental**. Connecting it uses your browser session's cookies,
which X's terms don't allow (see Terms risk).

The connector was released against maunium.net/go/mautrix v0.31.0; the bridge host runs
v0.33.0. Checked for breaks that still compile: every optional bridgev2 interface the
connector's types have methods for is still implemented with the v0.33 signature (connector:
direct media, transaction IDs; client: backfill with limits, edits, reactions, redactions,
read receipts, typing, mute, tags, room name and avatar, chat deletion, message requests,
identifier lookup, membership, push), it defines no remote event types of its own (only
`simplevent`, which moved with mautrix), has no database tables, upgrades or config
upgrader steps beyond copying its own keys, and uses no bridgev2 behaviour removed since
v0.31. It uses mautrix's beeper/req fork through the `replace` in `apps/bridge-host/go.mod`
(the version mautrix-meta names, newer than the one mautrix-twitter's own go.mod pins), for
the Chrome-impersonating transport every X request goes through; an anonymous request to
x.com through it works over HTTP/2 (`TestTwitterTransportReachesX`). Real traffic with an
account hasn't been tried yet.

The bridge host's setup is `apps/bridge-host/internal/networks/twitter.go`: the connector's
example config, with contact names as the display name (or the handle when there is none)
without the " (Twitter)" suffix, and `x: true` so the connector calls the network X. There are
no operator settings: nothing to put in `.env`, and the compose service (`bridge-twitter`,
profile `twitter`, database `bridge_twitter`) needs nothing beyond the shared bridge settings.

## Connecting an account

One flow is offered: **Paste cookies** (flow ID `cookies`). The connector's other flow,
username and password (`password`), isn't offered: it needs a browser token ("Castle
token") generated by running X's script in a hidden web view, which only Beeper's clients
can do.

1. Open a **private window** and sign in at <https://x.com/i/flow/login>.
2. Open the developer tools (F12): **Application** (Chrome) or **Storage** (Firefox), then
   **Cookies** → `https://x.com`.
3. Copy the values of **`ct0`** and **`auth_token`** into the app's two fields (both masked).
4. **Close the private window without logging out** (logging out ends the session), then
   press Continue.
5. The app then asks for your **X Chat passcode**, the 4-digit PIN that protects your
   encrypted messages' keys. The bridge uses it once to recover your X Chat keys from X's
   key backup (Juicebox).
   - X allows only a few wrong guesses; the step says how many are left. Too many locks X
     Chat for the account.
   - **If the account has never set up X Chat**, the step says so ("No PIN code is
     registered yet. Create your X Chat PIN below.") and whatever you enter **becomes your
     new X Chat PIN**: the bridge registers new X Chat keys on your account. Do that on
     purpose only, and remember the PIN; X's apps will ask for it.
   - The PIN field is a 2FA-code field, which the app shows in the clear rather than masked.

From the terminal (dev only, no gateway): `bridge-host --network twitter --dev-keys --user
<id> login` prompts for `ct0`, `auth_token`, then `Passcode`.

## What's stored in plaintext

Nothing beyond bridgev2's own tables (the connector has no tables of its own and writes no
files), but those hold the account's keys:

- **`user_login.metadata`**: the session cookies (`auth_token`, `ct0` and the others X sets),
  your **X Chat private keys** (`secret_key`, `signing_key` and its version) recovered with
  the PIN, Web Push keys, browser headers, a cached session (X's verification and animation
  tokens, a polling cursor), and inbox cursors. With the database, someone could act as the
  account and decrypt its X Chat messages fetched from X.
- **`portal.metadata`**: each X Chat conversation's keys (by key version) and conversation
  token, and whether it's trusted.
- **`message.metadata`**: an edit count and, for messages sent from the app, the client
  message ID. No content.
- bridgev2's tables hold conversation names and contact names, as for every network
  (docs/architecture/sealing.md, What else is stored in plaintext).

None of it is message content, so there's nothing to sweep; the keys go when the login is
deleted (log out).

Logging at the default level (info) carries no message content or contact names; it does log
your own account's handle once at connect ("Successfully loaded and authenticated as user").
A request X answers with a 4xx, or that fails before a retry, is logged at error level with
X's response body (an error description). At **debug** level (`--verbose`) the connector logs
whole request payloads, which for conversations that aren't encrypted include message text,
and at trace level raw incoming events. Never run X with `--verbose` in production.

## Sends and retries

twittermeow (`MakeRequestFull`) retries requests up to five times after a connection error or
a 5xx. As twittermeow is written at this version, a send can't go out twice that way: the
body is a reader that the first attempt consumed, so a retry after the request went out
carries an empty or partial body, which X rejects. (A retry after a connection that never
opened resends the whole body, but then nothing reached X.) The connector doesn't mark that
error certain, so the send is recorded as **delivery unknown**, not failed: a send X
received but answered with a 5xx may have been delivered, and you choose whether to send it
again.

Replies are sent with their target's IDs only, without X's quoted preview: the connector
fetches the replied-to message's text from Matrix, which the bridge host can't provide (it
keeps no content), so it falls back as it's designed to.

## Known limits

- Media from the app: images and GIFs up to 5 MiB, video up to 15 MiB. Voice messages aren't
  converted to Opus (no `ffmpeg` in the bridge host image).
- Edits only within 15 minutes, at most 10 times; edits and deletion for everyone only in X
  Chat conversations (legacy DMs support delete for me).
- On connect, the 20 most recent conversations are synced (`conversation_sync_limit`); a
  first sync of a large X Chat inbox runs in the background and can take a while.
- The cookies last as long as X keeps the session. When it ends (or X locks the account for
  checks), the login reports bad credentials; open x.com, clear any checks, and connect again.

## Terms risk

`termsRisk: true`. X's terms forbid accessing the service by automated means other than its
published APIs; using a browser session from a server can get the account locked or
suspended, and X may ask for verification (the connector reports a locked account as such).

## How to test

With Isaac's account:

- [ ] **Connect**: paste `ct0` and `auth_token`, enter the existing X Chat PIN; the login
      completes. (A wrong PIN once: the step comes back with the guesses left.)
- [ ] **Receive**: an X Chat message and, if the account still has any, a legacy DM, each in
      its chat with the sender's name.
- [ ] **Send**: a message from the app arrives in X's app; its status reaches `sent`.
- [ ] **Reply**: a reply from the app shows as a reply in X (without the quoted preview); a
      reply made in X shows its target in the app.
- [ ] **Edit**: an edit each way within 15 minutes.
- [ ] **React**: a reaction each way; removing it.
- [ ] **Delete**: deleting a message each way.
- [ ] **Media**: an image and a short video each way.
- [ ] **Backfill**: recent history of the newest conversations appears after connecting.
- [ ] **Message request**: a DM from someone you don't follow arrives; replying accepts it.
- [ ] **Group chat**: a message in a group arrives with the group's name.
- [ ] **Reconnect after restart**: restart `bridge-twitter`; messages sent meanwhile arrive.
- [ ] **Log out**: logging out in the app ends the login.
